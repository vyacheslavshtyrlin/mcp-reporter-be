# EPIC-003 — PostgreSQL persistence

**Статус:** согласован 26 октября 2026 года; реализация не начата.

## Цель и ценность

Заменить временное in-memory хранилище отчётов на PostgreSQL и добавить сохраняемые версионируемые определения отчётов. После Epic пользователь сможет получить запуск после перезапуска сервиса, безопасно повторить идемпотентный запрос, сохранить или обновить определение отчёта и запустить его по идентификатору.

Epic развивает учебные темы Prisma, миграций, транзакций, конкурентности, optimistic locking и lifecycle ресурсов NestJS, не вводя очередь и отдельный worker раньше предусмотренного этапа.

## Границы

### Входит

- локальный PostgreSQL 18 через Docker Compose;
- Prisma 7 и PostgreSQL driver adapter с зафиксированными совместимыми версиями;
- `PersistenceModule`, владеющий Prisma lifecycle и реализациями repository-контрактов;
- персистентные `ReportRun` и неизменяемые `ReportSnapshot`;
- атомарные переходы состояния и защита от конкурентного выполнения одного запуска;
- идемпотентность `run_report` по опциональному `clientRequestId`;
- сохраняемые определения отчётов с неизменяемыми версиями и optimistic locking;
- MCP tools для сохранения, обновления и просмотра определений и запусков;
- восстановление зависших `running`-запусков после старта одного процесса;
- integration- и MCP e2e-проверки с PostgreSQL.

### Не входит

- Redis, очередь, worker-процесс, leases и распределённое восстановление запусков;
- `OutboxEvent`, публикация событий и гарантированная доставка;
- состояние `cancelled` и повторный переход `running → queued`;
- отдельная таблица `DatasetSchema`;
- второй реальный источник данных;
- AI-summary и аналитика истории;
- production Dockerfile приложения, reverse proxy, TLS и production deployment;
- полноценный drain активных запросов при остановке процесса.

## Решения относительно design doc

Design doc предусматривает сущность `DatasetSchema`. В этом Epic отдельная таблица не создаётся: версия схемы сохраняется в версии определения отчёта, а эффективная конфигурация, нормализованные исходные записи, provenance и версия движка — в запуске и snapshot.

Польза решения — меньше связей и миграций до появления сценария управления несколькими реально изменяемыми схемами. Цена — пока нельзя независимо хранить и запрашивать историю схем dataset. Если такой сценарий появится, он потребует отдельного согласованного изменения модели данных.

Полный application-level drain отложен до этапа reliability/deployment. В текущий Epic входят корректное подключение Prisma, проверка доступности БД при старте и освобождение соединений при завершении Nest application.

## Требования

- **REQ-003-01.** `ReportRun` и его результат доступны после перезапуска приложения.
- **REQ-003-02.** Состояние `completed` и соответствующий `ReportSnapshot` сохраняются атомарно.
- **REQ-003-03.** Snapshot неизменяем; повторный запуск создаёт новый `runId`.
- **REQ-003-04.** Snapshot содержит итоговые строки отчёта и нормализованные наблюдения источника, достаточные для аудита результата.
- **REQ-003-05.** Переход `queued → running` атомарен: один запуск может забрать только один исполнитель.
- **REQ-003-06.** При старте одного процесса оставшиеся `running`-запуски переводятся в `failed` с кодом `PROCESS_INTERRUPTED`.
- **REQ-003-07.** Повтор с тем же `clientRequestId` и тем же payload возвращает существующий запуск; другой payload завершается `IDEMPOTENCY_CONFLICT`.
- **REQ-003-08.** Версии сохранённого определения неизменяемы.
- **REQ-003-09.** Обновление с устаревшим `expectedVersion` завершается `VERSION_CONFLICT`.
- **REQ-003-10.** Для запуска сохранённого определения разрешено переопределить только период.
- **REQ-003-11.** Prisma-модели не выходят за persistence seam и преобразуются в application/domain types.
- **REQ-003-12.** Локальная PostgreSQL-инфраструктура воспроизводимо запускается через Docker Compose.

## Публичный MCP-контракт

Добавляются tools:

- `save_report_definition`;
- `update_report_definition`;
- `list_report_definitions`;
- `list_report_runs`.

`run_report` расширяется двумя взаимоисключающими способами запуска:

1. inline-определение отчёта;
2. `definitionId` и период.

Также принимается опциональный `clientRequestId`. Без него каждый вызов создаёт новый запуск. Публичная форма `get_report_run` сохраняется, но источником данных становится PostgreSQL.

Точные Zod-схемы входов, пагинации и результатов будут зафиксированы до реализации MCP Feature и не должны раскрывать Prisma-модели.

## Архитектурные границы

```text
MCP transport
  → ReportExecutionService
  → ReportRunRepository (application interface + runtime DI token)
      → InMemory adapter (быстрые unit/contract tests)
      → Prisma adapter (runtime и integration tests)
          → PostgreSQL
```

`PersistenceModule` владеет Prisma client/соединением, repository adapters, транзакциями, миграциями и mapping между Prisma records и domain/application types.

`ExecutionModule` владеет состояниями запуска, разрешёнными переходами, orchestration, предметными ошибками и repository-интерфейсом. MCP остаётся transport boundary и не обращается к Prisma напрямую.

Сетевой запрос к World Bank и расчёт отчёта не выполняются внутри длительной DB-транзакции. Короткие транзакции защищают только связанные изменения состояния и данных.

## Итоговая приёмка Epic

- завершённый отчёт и его snapshot доступны после перезапуска приложения;
- сбой транзакции не оставляет `completed` без snapshot и не создаёт частичный результат;
- при конкурентном claim одного запуска ровно один исполнитель получает право на работу;
- одинаковый идемпотентный запрос возвращает существующий запуск, а несовпадающий payload — стабильный конфликт;
- версии определений остаются неизменяемыми, а stale `expectedVersion` отклоняется;
- все новые tools проходят e2e через настоящий MCP transport и PostgreSQL;
- миграции применяются на чистой БД и повторный deploy не создаёт изменений;
- Prisma освобождает соединения при закрытии Nest application;
- проходят относящиеся к Epic format, lint, typecheck, unit, integration, e2e, coverage и build checks;
- обязательный review проведён после каждой Feature и перед закрытием Epic; замечаний `blocker` и `major` не осталось.

## Риски и неизвестные

- Prisma 7 требует driver adapter и аккуратной интеграции с Nest lifecycle; совместимость точных версий проверяется в `PERSIST-01`.
- JSON/JSONB из БД остаётся недоверенным после чтения и должен проходить runtime-валидацию до входа в domain.
- Канонизация payload для идемпотентности должна быть детерминированной и учитывать только семантически значимые поля.
- Внешние вызовы внутри транзакции могут удерживать соединения и блокировки; границы транзакций должны оставаться короткими.
- Startup recovery в этом Epic корректен только для одного процесса; multi-process execution требует leases/queue на следующем этапе.
- Integration/e2e-набор требует доступного Docker и должен явно сообщать, если инфраструктура не поднята.
- Расширение `run_report` должно сохранить обратную совместимость существующего inline-сценария.
